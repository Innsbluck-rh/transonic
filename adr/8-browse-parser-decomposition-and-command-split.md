## 概要

- `src-tauri/src/browse_parser.rs` を共通 parser として維持しない判断を行った。
- browse 系の変換処理では、0.0.1 時点では OpenSubsonic/Subsonic API のレスポンスをできる限りそのまま尊重する。
- command 層の責務を整理するため、browse 関連の command は `src-tauri/src/commands` 配下へ分割を始める。

## 現状で確認したこと

### `browse_parser` は 1 ファイルで複数の責務を持っている

- 現在の `browse_parser` には、API payload の deserialize、配列/単体や string/number などの揺れ吸収、アプリ向けの補完や推定が同居している。
- `parse_music_directory()` や `parse_music_folders()` のような関数名だけでは、どの値がどのように変換されたかを呼び出し側から把握しにくい。
- その結果として、command 側では一行で処理が完了して見える一方で、実際にはデータの補正や意味づけが隠れている。

### 補完や推定は parse よりも解釈に近い

- `title` が無いときに別の field を代用する処理や、`mediaType` を別の情報から推定する処理は、単なる parse ではなくアプリ都合の解釈である。
- これらが共通 parser に入っていると、どの command でも同じ補完や推定が自動で適用される。
- 初期実装段階でこのような補正を共通化すると、純粋な API レスポンスとの差分が見えにくくなる。

### browse 系 command の配置も責務が混ざりやすい

- 現在の browse 関連処理は `commands.rs`、`folder_structure.rs`、`browse_parser.rs` に分散しており、入口、変換、解釈の境界が読み取りにくい。
- index 一覧を返す command と、個別ページで使う詳細取得 command も分離されておらず、役割が混ざりやすい。

## 今回決めたこと

### `browse_parser` は完全に解体する

- `src-tauri/src/browse_parser.rs` は共通 parser として残さない。
- browse 系の変換処理は、責務ごとに分けて各 command または endpoint ごとの小さな helper に移す。
- 少なくとも、deserialize、型揺れの補正、アプリ都合の意味づけを 1 ファイルにまとめる構成は採用しない。

### 0.0.1 時点では API レスポンスをできる限り尊重する

- 現段階では、API から値が来ていない場合にアプリ側で積極的な補完や推定を行わない。
- 値が欠けている、型が揺れている、表現が不統一であるといった事情があっても、まずは純粋なレスポンスとの差分を見える形で扱う。
- ユーザ依存のデータ欠損が UX/UI に大きく影響すると判明した場合に限り、その時点で補正の要否を別途判断する余地は残すが、0.0.1 の判断としては採用しない。

### 補正が必要なら隠さず局所化して書く

- API の揺れを吸収する処理は、汎用 helper を過度に増やすよりも、対象 endpoint が明確に分かる場所へ書くことを許容する。
- 型の補正や値の変換が必要な場合は、どの field をどう扱ったかが読める形で API 呼び出しを行う command のその場に明示する。
- 「parser を一回通したので整っている」という前提は置かない。

### adapter のような外部変換層は導入しない

- 現段階では、データの変更や修正を adapter や外部変換ファイルへ委譲しない。
- 変換専用の層を早い段階で追加すると、どこでデータが変わったかが追いにくくなるため採用しない。
- どうしても補正が必要な場合は、その API を呼び出している command のその場で明示的に書く。

### command 層は `commands` 配下へ分割を始める

- browse 関連の command は `src-tauri/src/commands` 配下へ分割する方針を採用した。
- index を返す処理と、個別の id ページで使う処理は分けて配置する。
- `commands.rs` には入口の集約だけを残し、browse 系の責務は個別ファイルへ寄せる。

## 所感

- 現在の `browse_parser` は「外部レスポンスの decode」「揺れの補正」「アプリ都合の解釈」を一つの関数呼び出しに圧縮しており、読み手に対して不透明だった。
- 初期実装の段階では、レスポンスを整えすぎるよりも、どこで何が変わったかを明示する構成の方が判断しやすい。
- browse 系の command を `commands` 配下へ分けることで、index と詳細の責務、変換の置き場、アプリ都合の補正の有無を追いやすくなる。
