## 概要

- ASIO 出力を再度扱うにあたって、ADR-19 が関門として指定した「pause 処理とコールバック到達性の確認」を実機で行った。
- ADR-19 が記録していた現象は pause でのみ発生し、drop では発生しないことが分かった。
- 現象の原因は Transonic 側ではなく cpal の ASIO ホスト実装にあったため、vendoring している `src-tauri/crates/cpal` に修正を入れることにした。
- 検証の途中で、当初の目的とは別の不具合と性能上の問題を cpal 側に2件見つけたので、あわせて修正した。
- 検証は Windows 実機で行った。使用したドライバは Audient USB Audio ASIO Driver、ASIO4ALL v2、Realtek ASIO である。

## ビルド基盤について決めたこと

- `src-tauri/crates/asio-sys` にあったローカル patch crate (0.2.6) を削除した。vendoring している cpal 0.18.1 が要求するのは `asio-sys` 0.3.0 であり、バージョンが一致しないためこの patch は適用されていなかった。`Cargo.lock` にも `[[patch.unused]]` として記録されていた。
- 削除にあたって、この patch crate が持っていた細工のうち bindgen の `layout_tests(false)` は不要だと確認した。0.3.0 をそのまま使って `cargo check --features windows-asio` が通る。
- 一方で libclang のパスを NDK から補う細工は、削除時点の開発環境では必要な機能を果たしていた。このマシンには単体の LLVM が入っておらず、bindgen が libclang を見つけられなかった。これはクレート側の問題ではなく開発環境の問題であると判断し、patch crate を復活させるのではなく LLVM を単体でインストールして解決した。
- ASIO SDK は `asio-sys` 0.3.0 の build script による自動ダウンロードで取得した。取得先は Steinberg の公式配布である。ダウンロード先は `%TEMP%` でありディスククリーンアップで消えるため、`C:\Users\innsb\asiosdk` へ移動し、以降は `CPAL_ASIO_DIR` で明示している。
- `src-tauri/Cargo.toml` の workspace 設定で `crates/cpal` を `exclude` に加えた。vendoring したクレートに手を入れる以上、その場で `cargo test` や `cargo run --example` を実行できる必要がある。従来は member でも exclude でもなかったため、`crates/cpal` の中で cargo を実行できなかった。

## 実機で確認した現象

- ASIO ストリームを再生した状態から `Stream::pause()` を呼ぶと、無音にならず、直前に鳴っていた音が短い周期で反復し続けた。Audient で再現した。
- 反復の周期は理屈と一致する。ASIO はチャンネルごとに2枚のバッファを持ち、cpal が pause 中に何も書かないため、ドライバは古い2枚を切り替え続ける。バッファサイズ 256 frames、44100Hz であれば 512 frames、約11.6ms の周期で反復する。
- 再生中のストリームを drop した場合は無音になった。ADR-19 は pause と stop と drop の3つを併記していたが、実際に問題があるのは pause だけである。
- ドライバの起動遅延には機種差が大きい。`play()` から最初のバッファコールバックまでが Audient では 6ms、ASIO4ALL では約400msだった。

## cpal に入れた修正

### pause 中に無音を書く

- ASIO の出力コールバックは、再生状態が Playing でない場合にバッファへ何も書かずに早期 return していた。これを、対象バッファを無音で埋めてから return するように変更した。
- 無音化は既存の `current_callback_flag` の仕組みを経由させた。ASIO は1つのドライバの出力バッファを複数の cpal ストリームで共有しうる構造であり、既存実装は「バッファ切り替えごとに最初のコールバックが1回だけ無音化し、以降のストリームはそこへ加算する」という前提で整合を取っている。pause 中のストリームが無条件に無音化すると、同じデバイスで再生中の別ストリームの音を消す可能性があるため、この前提に合わせた。
- 無音化はサンプル形式を問わず生バイトをゼロで埋める形で実装した。ゼロのビットパターンは ASIO が報告しうるすべてのサンプル型と、どちらのエンディアンでも無音になる。24bit の3バイトサンプルでも正しく無音になる。
- 入力ストリーム側の早期 return は変更していない。入力はハードウェアへ書き込まないため、コールバックを呼ばないことに害がなく、上流との差分を小さく保つことを優先した。
- 修正後、Audient と ASIO4ALL の両方で pause 中に無音になることを実機の聴取で確認した。

### `device_by_id` をホスト側で実装する

- ASIO ホストは `device_by_id` を実装しておらず、`HostTrait` の既定実装にフォールバックしていた。既定実装は全デバイスを列挙して id が一致するものを探すため、ASIO では登録されている全ドライバを順にロードして破棄する動作になっていた。
- この動作は保存済みデバイスの解決、つまりトラックのロードごとに走る経路に乗る。検証環境では登録7本のうち3本しかロードできず、失敗するドライバの待ち時間を含めて列挙全体に1.7秒かかっていた。
- 速度以上に問題なのは、目的のドライバに到達するまでの過程で、ユーザーが選んでいないドライバをロードして破棄することである。検証環境では ASIO4ALL v2 がこの経路に入っていた。ASIO4ALL は WDM デバイスのラッパーであり、他の出力に干渉する可能性がある。
- ASIO の `DeviceId` はドライバ名をそのまま保持しているため、名前を指定してそのドライバだけをロードする実装に置き換えた。Audient の解決時間は1.7秒から0.45msになった。
- あわせて、ドライバのメタデータを読み取る処理を `Device::from_loaded_driver` として切り出し、列挙とこの新しい経路で共有するようにした。

### `Drop for Stream` がバッファスロットを解放していなかった

- 同じ `Device` から2本目の出力ストリームを構築すると、1回おきに `hardware input or output is not present or available` で失敗した。8回試して4回失敗し、成功と失敗が完全に交互になった。待ち時間を0ms、50ms、200msと変えても失敗率は変わらなかったため、競合ではなく状態の問題だと判断した。
- 原因は、`Drop for Stream` がコールバックの登録解除だけを行い、`Device` が持つ `asio_streams` の記録を消していなかったことである。ASIO のバッファはドライバの破棄時に解放されるため、この記録は解放済みのバッファを指したまま残る。次のストリーム構築では `get_or_create_output_stream` がバッファは既にあると判断してその作成を飛ばし、続く `driver.start()` が失敗する。そして失敗経路が記録を消すため、次の試行は成功する。これが交互に失敗する仕組みである。
- `Stream` が自分の持ち分を判別できるように向きを保持させ、`Drop` でその側の記録を消すようにした。これは `driver.start()` の失敗経路が既に行っている後始末と同じ内容である。
- 修正後、8回連続で構築に成功した。
- なお現状のアプリ側の実装はこの不具合を踏んでいなかった。`build_cpal_stream` が毎回 `resolve_cpal_output_device` を呼んで新しい `Device` を作るため、`asio_streams` の記録も毎回新しくなっていたからである。ただし解決済みの `Device` を再利用すると1回おきに再生が失敗する状態だったため、潜在的な問題としては存在していた。

## 上流との乖離について

- vendoring したクレートに手を入れる以上、次に cpal を更新するときのリベース費用を自分たちで負担することになる。これは pause の問題を正しい層で解決するための対価として引き受けることにした。
- 3件はいずれも cpal 単体で見ても不具合または改善であり、Transonic 固有の都合を持ち込んだ変更ではない。上流へ還元できる性質のものである。
- 変更範囲は `src-tauri/crates/cpal/src/host/asio/` の3ファイルに収まっている。アプリ側のコードには ASIO 固有の処理を追加していない。ADR-18 の実装が pause や stop の特殊処理をアプリ側の WASAPI 経路に混ぜてしまったのに対し、今回は同じ問題を cpal の内側に閉じ込めた。この結果、アプリから見た `pause()` と `play()` と drop の意味が WASAPI と ASIO で同一になり、`pause_active_session` や `tear_down_active` に手を入れる必要がなくなった。

## 検証の途中で分かったその他のこと

- ASIO の `default_output_config()` が返すサンプルレートは信頼できない。Realtek ASIO はストリームが動くまで 0 を返した。また Audient は最初 96000 を報告していたが、検証で 44100 のストリームを開いた後は 44100 を報告するようになった。cpal は要求されたレートを `set_sample_rate` でドライバへ設定するため、この値は自分の再生によって書き換わる可変の状態である。
- ASIO のサンプル形式はドライバ固有で、しかも F32 だけではない。Audient と ASIO4ALL は I32、Realtek は I24 を報告した。ASIO は符号なし形式を扱わないため、I16、I24、I32、F32 の4種類が対象になる。
- 列挙に出てくることは使用できることを意味しない。Realtek ASIO はチャンネル数とサンプルレートを何に変えても構築に失敗した。WASAPI 側の一覧に Realtek のアナログ出力が存在しないため、ドライバは読み込めるがハードウェアが無い状態だと考えられる。
- ASIO4ALL v2 が報告するチャンネル数は、その時のダッシュボード設定によって変わった。検証中に8chから2chへ変化している。
- cpal は ASIO の最初のデバイスを既定デバイスとして扱う。検証環境では ASIO4ALL v2 が該当した。WDM のラッパーが既定になるため、ASIO を既定出力の代替先として使うべきではないという ADR-19 の判断は妥当である。
- ドライバのロードと構築にかかる時間は機種差が非常に大きい。Audient は解決も構築も1ms未満で済むが、ASIO4ALL は解決に1.9秒から2.6秒、構築に0.4秒程度かかった。また Audient でもプロセス内で最初の1回だけは構築に約0.9秒かかった。
