## 概要

- Windows の出力に ASIO を追加した。ADR-19 で一度スクラップした機能を、WASAPI の出力デバイス切り替えが安定した状態から作り直したものである。
- ADR-19 が「ASIO を再度扱うなら別機能として再設計する」と決めたとおり、ADR-18 の実装を継ぎ足してはいない。
- ADR-18 との最大の違いは、ASIO 固有の面倒をアプリ側に持ち込まなかったことである。pause や drop の特殊な扱いは vendoring した cpal の内側で解決した。その経緯と実測は ADR-24 に記録した。
- 実機で確認した。使用したのは Audient iD14 MkII の ASIO ドライバで、44.1kHz、48kHz、96kHz の 24bit FLAC を再生した。

## 有効化の方法と公開の仕方

- ASIO は Cargo feature `windows-asio` による opt-in のままにした。既定のビルドには含まれない。
- ビルドには ASIO SDK と libclang が必要になる。開発環境の準備については ADR-24 に書いた。
- `PlaybackCapabilities` に `asioOutput` を戻した。値は `cfg!(feature = "windows-asio")` である。ADR-19 でこの capability を削除したが、ASIO を含まないビルドで ASIO の UI を出さないためには、ビルドに ASIO が入っているかどうかをフロントエンドが知る必要がある。
- 設定に `useAsioOutput` を追加した。既定は false である。ASIO はデバイスを排他的に掴み Windows のミキサーを迂回するため、求めていない利用者に既定で与えるものではないと判断した。

## デバイスの一覧と選択

- `PlaybackOutputDevice` に `host` を追加した。値は `wasapi` か `asio` である。ADR-18 は同じ情報を持っていたが、ADR-19 で削除していた。
- 一覧では WASAPI のデバイスを先に、ASIO のデバイスを後に並べる。それぞれの中では表示名で並べる。
- UI ではドロップダウンの見出しによる分類は行わず、ひとつの平坦な一覧にしたうえで ASIO のデバイスだけ `ASIO: ` を前置する。ADR-18 では見出しによる分類を行っていたが、扱いが面倒な割に得るものが少ないため採らなかった。WASAPI 側に前置きを付けないのは、ASIO の表示を `Use ASIO Output` のチェックボックスで出し入れするため、非対称であることがそのまま意味を持つからである。
- `Use ASIO Output` は `Use Custom Output` の下位の設定として扱う。`Use Custom Output` を切り替えたときは、その方向にかかわらず `useAsioOutput` を false に戻す。これを行わないと、チェックボックスが隠れている間に値が残り、次に `Use Custom Output` を有効にしたときに ASIO が黙って復活する。実際にこの挙動に遭遇して分かりにくかったため、リセットする形にした。
- 保存済みの `outputDeviceId` が ASIO のデバイスを指していても、`useAsioOutput` が false の間は再生に使わない。`effective_output_device_id` で判定している。UI は `Use ASIO Output` を切るときに選択も消すが、設定ファイルを直接書き換えられる可能性があるため、設定の層でも同じ判断をしておく。

## ASIO デバイスの列挙をいつ行うか

- ASIO の列挙は要求されたときだけ行い、結果はプロセスの生存期間中ひとつだけ保持する。
- 列挙は登録されているすべての ASIO ドライバを順に読み込んで初期化するため、ハードウェアが無いドライバが失敗するまでの待ち時間を含めて時間がかかる。開発環境では登録7本に対して1.7秒だった。さらに、利用者が選んでもいないドライバに一時的にハードウェアを渡すことになる。ASIO は同時にひとつのドライバしか読み込めないため、ASIO で再生している最中に列挙すると一覧が途中で切れるという問題もある。
- 起動時に必ず列挙する案は採らなかった。ASIO を使わない利用者にこの費用を負わせないためである。
- 一度だけ列挙する代償として、起動後に接続したデバイスはアプリを再起動するまで一覧に出ない。ASIO の機材は据置が主で抜き差しの頻度が低いため、この代償を受け入れた。

## 列挙の要求を引数にした理由

- `playback_get_output_devices` は ASIO を含めるかどうかを引数で受け取る。
- 当初は保存済みの設定を Rust 側で読む実装にしていた。フロントエンドが要求するだけで重い列挙を起こせないようにする意図だったが、これは誤りだった。
- フロントエンドの設定更新は、ストアを先に更新してから設定コマンドを待つ。したがってストアの変更で走る再取得のほうが、設定のコミットより先に到着する。その結果 `use_asio_output` はまだ false と読まれ、ASIO のデバイスが入らない一覧が返る。そしてコマンド完了後にストアへ同じ値が入るだけなので、再取得の契機は二度と来ない。
- この不具合は ASIO を有効にする向きでのみ現れ、無効にする向きでは正常に見えた。無効にするときは Rust 側がまだ true を返すが、フロントエンドのフィルタが ASIO を落とすため結果が偶然正しくなるからである。この非対称性のせいで、最初は修正済みだと誤って判断した。
- 引数にすれば競合そのものが存在しなくなる。フロントエンドがどの状態を要求しているかは、要求した本人が知っている。
- 列挙を求めてよいかという判断と、ASIO のデバイスで実際に再生してよいかという判断は別のものである。後者は保存済みの設定に対して `effective_output_device_id` が引き続き決めており、引数化によって弱まってはいない。

## ストリームの構成をどう決めるか

- WASAPI の経路は変更していない。共有モードなので、ソースのチャンネル数とサンプルレートをそのまま要求し、Windows のミキサーが合わせる。
- ASIO にはミキサーが無いため、ドライバに対して構成を交渉する必要がある。サンプル形式はドライバが報告するものに従い、チャンネル数はドライバの上限で切り詰め、サンプルレートは対応しているものから選ぶ。
- サンプルレートはソースのレートを優先して要求する。cpal はデバイスのクロックを要求されたレートへ切り替えるため、これがリサンプリングを経由しない経路になる。ソースのレートに対応していない場合だけ、対応表から最も近いものを選ぶ。
- `default_output_config()` が返すサンプルレートは選択の材料に使っていない。ストリームが動くまで 0 を返すドライバがあり、しかもこの値は自分の再生によって書き換わるためである。詳細は ADR-24 に書いた。
- チャンネル数は、デバイスが許す限り2を下回らないようにしている。モノラルの音源であっても1チャンネルのストリームは開かない。ASIO には1チャンネルを複数の出力へ広げるミキサーが無いため、1チャンネルのストリームはハードウェアの最初の出力からしか聞こえない。WASAPI では Windows のミキサーがモノラルを両方のスピーカーへ広げるので、出力経路の選択によって聞こえ方が変わってしまう。出力側で2チャンネル以上を開けば、モノラルの音源を複製する処理は既存の `map_source_frame` が行う。
- 出力のサンプル形式は I16、I24、I32、F32 を扱う。ASIO は符号なしの形式を持たないため、これで全域である。ADR-18 が列挙していた I8、I64、U8、U16、U24、U32、U64、F64 は ASIO には現れない。
- 内部の PCM は従来どおり f32 で描画し、出力の直前で変換する。リサンプリングとチャンネルの対応付けは、gapless のために既に存在していた `OutputWriter` と `OutputResampler` をそのまま使っている。ADR-18 ではこの部分を ASIO のために書いたが、今回は書く必要が無かった。

## 解決したデバイスを保持する

- `outputDeviceId` から `cpal::Device` を解決した結果を、ASIO のデバイスに限ってプロセス内に保持する。
- 解決はトラックの読み込みごとに走る。ドライバによっては読み込みに時間がかかり、開発環境では Audient が0.5ミリ秒、ASIO4ALL が1.9秒から2.6秒だった。後者のようなドライバでは、保持しなければトラックを切り替えるたびに数秒待たされる。
- WASAPI のデバイスは保持していない。解決が速いので利点が無く、機器の抜き差しで無効になったハンドルを抱え込む危険のほうが大きい。
- 同じ `Device` を使い回して次々にストリームを作る形は、ADR-24 で直した cpal の不具合を踏んでいたため、修正前は成立しなかった。

## keep-alive との関係

- ASIO のデバイスが選ばれているときは、ADR-22 で導入した無音の keep-alive ストリームを開かない。
- ASIO のドライバはひとつの出力ストリームしか許さないため、再生用のストリームと並べてもう一本開くことが構造的にできない。
- そもそも不要でもある。ASIO のドライバはストリームが存在する限りバッファを切り替え続け、一時停止中のストリームはそこへ無音を書き込む。ADR-24 の修正によって、一時停止中も含めてデバイスは動き続けている。
- ただし最初の再生より前と、停止してストリームを畳んだ後は、デバイスがアイドルに入りうる。ADR-22 が対象とした「アイドル明けにフェードインが乗る」現象は、この区間では ASIO でも起こりうる。ASIO の機材は電源が常時供給される据置が主であり、ADR-22 が対象とした省電力の USB や Bluetooth の DAC とは母集団が違うため、ここは埋めないことにした。

## 実機で確認したこと

- 44.1kHz、48kHz、96kHz の 24bit FLAC を再生できた。Audient のサンプル形式は I32 である。
- 44.1kHz から 96kHz、48kHz へと異なるレートのトラックを移動しても、デバイス側のレート設定と再生ストリームのレートが正しく追従した。
- gapless の準備が ASIO でも成立した。
- 一時停止で音が途切れず反復する現象は起きなかった。ADR-24 の修正が実際の再生経路でも効いている。
- 再生しながら WASAPI と ASIO を相互に切り替えられた。
- ハードウェアが存在しない ASIO デバイス（開発環境の Realtek ASIO）を選ぶと `Failed to load playback stream: Audio output device error: failed to build output stream: hardware input or output is not present or available` として一時停止状態になり、有効なデバイスに戻せば再生を再開できた。列挙に出てくることが使用できることを意味しないため、この経路は通常起こりうる。
- モノラルの音源が両方の出力から鳴ることを確認した。44.1kHz 16bit と 48kHz 24bit の両方で確認している。
- 左右の判別用の音源で、左のみ、右のみ、両方の順に意図どおり鳴ることを確認した。チャンネルが入れ替わっていないことも含めて確認できている。同じ音源を WASAPI でも再生して結果が一致することを確かめた。
- ASIO4ALL v2 を選んでも再生できた。最初の選択には数秒かかるが、その後のトラックの切り替えは速いままだった。解決した `Device` を保持している効果である。
- ASIO を含まないビルドでも従来どおり動作した。ASIO の UI は現れず、WASAPI の出力デバイス選択は変わらず使える。
- ASIO を含まないビルドで、保存済みの出力デバイスが ASIO のものだった場合は `Unavailable output` として表示される。勝手に既定のデバイスへ読み替えることはしない。この挙動は、保存した出力先を黙って別のものに差し替えないという ADR-19 の判断と一致しており、望ましいものだと判断した。

## 検証用の音源について

- 当初の検証は手持ちの音源で行ったため、レートやチャンネル数を狙って揃えることができなかった。この過程で、再生中のレート表示を読み違えて異常があると誤認しかけたことがあった。
- そこで ffmpeg で検証用の音源を作った。モノラルを2種類（44.1kHz 16bit と 48kHz 24bit）、左右の判別用を2種類（44.1kHz と 96kHz の 24bit）である。左右の判別用は最初の5秒が左のみ、次の5秒が右のみ、最後の5秒が両方という構成で、チャンネルの入れ替わりや複製が耳で分かるようにしてある。
- これらの音源はこのブランチには含めていない。ASIO の実装と検証基盤の整備は別の作業であり、混ぜると双方の検証範囲が曖昧になるためである。レートとチャンネル数とビット深度を組み合わせた音源一式は、Android の再生経路や将来の変更でも役に立つので、独立して用意する価値がある。

## モノラルの扱いについて検証前に見つけたこと

- 検証用の音源を用意している最中に、モノラルの音源で1チャンネルの ASIO ストリームを開いてしまう問題に気づいた。この状態では左からしか聞こえない。
- 実際に再生して見つけたのではなく、モノラルの音源を渡したときに何が起きるかを追って気づいたものである。チャンネル数を2以上にする修正を入れてから検証に回し、修正後の動作を実機で確認した。

## 併記

- 検証の途中で `cover_art_cache.rs` の並行取得のテストが一度だけ失敗した。遅延する HTTP サーバへ4つのスレッドから同時に要求するテストで、単独で繰り返しても全体を通しても再現しない。今回の変更とは関係が無い既存の不安定なテストだと判断している。
- ASIO を含まないビルドで、保存済みの出力デバイスが ASIO のものだった場合、keep-alive のストリームを開こうとして `invalid output device id: host "asio" is not supported on this platform` の警告が出る。keep-alive の失敗は致命的として扱っていないので警告だけで済み、再生そのものは有効なデバイスを選び直せば動く。この状態では ADR-22 のフェードイン対策が効かないが、そもそも出力先を選び直す必要がある状態なので、これ以上の手当てはしていない。
