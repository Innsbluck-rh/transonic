## 概要

- 一部の省電力 USB/Bluetooth DAC で、再生開始時に曲の頭へフェードインが乗る現象があった。手元では Shanling UP4（USB 有線, WASAPI, デュアル ES9218P）で再現し、Audient iD14 MkII（WASAPI, CS43198）では出なかった。
- 原因は Transonic 側ではなく DAC 側だった。UP4 はオーディオストリームがアイドルになると出力段をオートミュートし、次の再生でストリームが張られたときにポップ防止のソフトミュート解除ランプをかけながら復帰する。このランプが曲頭に重なってフェードインとして聞こえていた。
- 実機で切り分けた。裏で別アプリに無音を鳴らし続けて UP4 を起こしたままにするとフェードが消えることを確認し、DAC のアイドル明け復帰が原因であると特定した。
- 対策として、Windows の symphonia バックエンドに「ワーカー生存中ずっと保持する無音の keep-alive 出力ストリーム」を追加し、選択中の出力デバイスを常に起こしておくことにした。

## 決定

- `windows_symphonia` の active worker が、ゼロ書き込みの無音 cpal 出力ストリームを 1 本、ワーカーが生きている間ずっと保持する。
- ワーカー起動時に既定デバイスでこのストリームを開き（プリウォーム）、`SetOutputDevice` で出力デバイスが実際に変わったときだけ新しいデバイスへ張り直す。デバイス id が変わらない場合は張り直さない。
- keep-alive ストリームは停止・一時停止・`Load`・`Stop` のいずれでも畳まない。アプリが生きている間は DAC を寝かせない。ワーカーのチャネルが閉じる（実質的なアプリ終了）ときにスコープアウトで解放される。
- keep-alive ストリームは `default_output_config()` のフォーマットと F32 で開く。トラック再生用ストリームとは独立に持ち、共有モード WASAPI なので両者は併存する。
- keep-alive の構築失敗は非致命として扱い、ログ警告のみ出す。keep-alive が無くても再生自体は動作し、フェード抑制が効かなくなるだけである。

## 退けた案とその理由

- 「再生開始の直前に無音を数百 ms 流してから本番 PCM を入れる」プリロール案はデフォルトにしないことにした。必要なプリロール長は DAC 固有のランプ長に依存して一般化できず、その計測値をユーザー設定として入力させるのは UX として成立しないためである。
- 「停止後もしばらく keep-alive を維持し、一定アイドルで解放する」linger 案は退けた。この案では起動直後の初回再生と、長い一時停止のあとの再生という、もっとも目立つ 2 ケースでフェードが復活してしまい、曲間の切り替えしか救えないためである。
- ブラウザが常にフェードしないのは、無音の間もレンダーストリームを開けっぱなしにしているためであると分かった（Chrome は一時停止後およそ 10〜15 秒保持してから解放、Firefox はほぼ無期限に保持する例がある）。素の常駐 keep-alive はこの挙動に倣ったものである。Transonic の既定姿勢としては再生の鮮度を優先する。

## 確認できたことと併記事項

- 実機（UP4, USB 有線, WASAPI）でフェードの消失を確認した。release ビルドでは UP4 の抜き差しや Transonic の再起動を挟んでも再発しなかった。
- dev ビルドのまったくの初回起動時に、keep-alive ストリーム開始のタイミングで一瞬プツンという音がした可能性がある。ただし release ビルド・再起動・抜き差しでは再現しなかった。DAC の電源投入時の過渡音が無音の上に乗ったものと推測しており、音楽ではなく無音に乗るため害は無いと判断した。
- 既知の副作用として、keep-alive を保持している間は出力デバイスがオートスリープやオートパワーオフに入らない。同種の「アプリがデバイスを掴んで省電力を妨げる」挙動は Chrome や Firefox でも報告されており、Windows の据置・有線環境では実害が小さいと判断した。バッテリー切迫が本当に問題になるのはスマートフォンであり、そちらは別の再生実装が扱う。
- 他アプリが WASAPI 排他モードで同一デバイスを掴むと、この常駐共有ストリームが干渉しうる。ニッチな状況であるため、今回の対象外とした。
