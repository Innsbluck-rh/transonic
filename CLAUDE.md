# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Transonic is a multi-platform (desktop + Android) music player client for Subsonic/OpenSubsonic servers, built with Tauri 2 (Rust backend) + SolidJS (TypeScript frontend). An optional standalone Go server (`server/`) provides "Connect" features (multi-device presence, shared playback, remote control) — it never touches media files or the upstream OpenSubsonic library; it only brokers sessions against the user's existing OpenSubsonic credentials.

Always consult the latest (Open)Subsonic API docs (`docs/OpenSubSonic/`) for endpoint compatibility — do not assume from memory.

## Commands

Frontend (run from repo root):
- `pnpm dev` — run `tauri dev` (desktop). `predev` auto-runs bindings export first.
- `pnpm ad:dev` — `tauri android dev`
- `pnpm test` — run all vitest tests (`vitest run`)
- `pnpm test <path>` / `pnpm exec vitest run <path>` — run a single test file
- `pnpm format` / `pnpm format:check` — Prettier
- `pnpm bindings:export` — regenerate `src/bindings.ts` from Rust specta annotations
- `pnpm bindings:check` — verify bindings are in sync (also runs before `pnpm build`)
- `pnpm go-types:export` — regenerate the Go server's Connect wire types (`server/internal/realtime/connect_types_gen.go`) from the Rust source of truth via typeshare (requires `cargo install typeshare-cli --features go`)
- `pnpm go-types:check` — verify the generated Go types are in sync (not wired into `prebuild`; run in the Go server's CI)

Rust backend (prefer these pnpm wrappers over raw `cargo` so paths/manifest resolve correctly):
- `pnpm cargo:check` — `cargo check` in `src-tauri`
- `pnpm cargo:test` — `cargo test` in `src-tauri`
- Do **not** run a full `tauri build`/`tauri android build` unless truly needed — it is slow. `cargo check` + `cargo test` + `tsc` catch most issues.

Platform-gated Rust code (`#[cfg(target_os = "...")]` for `android`/`ios`) is **not** exercised by `pnpm cargo:check` on Windows:
- For Android Rust changes, verify with `pnpm tauri android android-studio-script --target aarch64` (target names: `aarch64`, `armv7`, `i686`, `x86_64` — not Rust triples). Do not use raw `cargo check --target aarch64-linux-android`; it bypasses Tauri's Android build setup and NDK wiring and can fail for unrelated reasons.
- For other non-Android platform-specific Rust code, try `cargo check --target <triple>` where appropriate.
- If a platform check can't run (missing toolchain/NDK/target), say so explicitly and state the exact command that should be run instead of silently treating a host-only `cargo check` as full verification.

Go server (`server/`, independent module):
- `go test ./...`, `go run ./cmd/transonic-server serve --config ./config.json` (see `server/README.md`)

Exclude `./third_party` (vendored androidx-media) from broad greps/searches — it's noise.

## Architecture

### Three-tier split

1. **`src-tauri/crates/opensubsonic-client`** — low-level OpenSubsonic/Subsonic HTTP client. One client instance = one server + one auth. Only does request building, envelope decoding, and API-error mapping. No app state, no profile/secret storage, no UI-facing result types. See `docs/opensubsonic-client-design.md` for the intended category-trait-per-endpoint-group design (`SystemApi`, `BrowsingApi`, etc.) and the phased endpoint rollout. Note: per `adr/20-implementation-garbage-audit.md` #7, several categories (browsing/lists/search) still leak raw `serde_json::Value` and compat parsing (`RawSong`, `vec_or_single`, etc.) into `src-tauri/src/commands/browse/*` rather than the client crate — be aware the design doc is aspirational in places.
2. **`src-tauri/src/{session,connect,connection,profiles,secrets}.rs`** — connection orchestration, active session, saved profiles, credential storage (`keyring` on Windows/macOS/Linux). Combines low-level client calls (`ping`, extensions, token info) into app-facing connect/reconnect flows.
3. **`src-tauri/src/commands/*`** — Tauri command boundary (`#[tauri::command]`), one module per feature area (`browse`, `playback`, `connect`, `settings`, `session`, `search`, `cover_art`, `artist_image`, `backup`). Re-exported through `src-tauri/src/commands.rs`.

Frontend (`src/`) is a SolidJS SPA: `features/*` holds services/hooks per domain, `stores/*` holds global Solid stores (`createStore`), `components/*` and `routes/*` are presentation, `layouts/*` picks desktop vs. smartphone (`sp`) shells based on `utils/isSP.ts`. Desktop and mobile route trees are both defined in `src/App.tsx` and are largely parallel (`/browse/...` vs `/sp/browse/...`).

### Type bridge: Rust ⟷ TypeScript

`src-tauri/src/bindings.rs` uses `tauri-specta` to define the invoke handler and generate `src/bindings.ts` (commands + types) from Rust `#[specta]`-derived types. **Never hand-edit `src/bindings.ts`** — it's regenerated by `pnpm bindings:export` and there's a `check-bindings` binary (`pnpm bindings:check`) that fails CI/build if the checked-in file is stale. After changing any `#[tauri::command]` signature or a type it references, rerun `pnpm bindings:export`.

There is a second, parallel bridge for the Go server: the Connect wire types (`ConnectPlaybackState`, `ConnectPlaybackCommand`, `PlayingState` in `src-tauri/src/models/`) are annotated `#[typeshare]` and generated Rust→Go into `server/internal/realtime/connect_types_gen.go` via the typeshare CLI (config in `typeshare.toml`). **Never hand-edit `connect_types_gen.go`** — regenerate with `pnpm go-types:export` and verify with `pnpm go-types:check`. `queue` entries stay opaque (`json.RawMessage`) on the Go side because the server never touches media.

### Playback architecture (the most complex subsystem)

Decided in `adr/10-playback-architecture-v1.md` and elaborated in `adr/16`–`adr/21`:

- **Rust backend is the single source of truth** for playback state (play/pause/seek/stop/next/prev, queue, current position). The frontend only issues commands and renders what Rust reports — it must not maintain its own "is playing" or queue authority.
- **Queue is an ordered array; current position is a queue index**, not a song ID — the same song ID can appear multiple times in the queue as distinct entries.
- **OS-specific playback is confined behind `src-tauri/src/playback/backend_shims/`** (`PlaybackBackend` trait in `backend.rs`). Per-OS implementations: `windows_symphonia.rs` (Windows, Symphonia decode + CPAL output + WASAPI device selection), `android.rs` (delegates into the Kotlin/Media3 side via JNI), `unsupported.rs` (other targets, no-op). `windows_mf.rs` is a shelved MediaFoundation experiment not currently wired up (see `adr/16`).
- `src-tauri/src/playback/controller.rs` is the central `PlaybackController` orchestrating backend, reporting, queue sync, and persistence (`playback_state.rs`).
- Server playback reporting is capability-gated: uses OpenSubsonic `reportPlayback` when the `playbackReport` extension is present, otherwise falls back to Subsonic `scrobble`. Neither is required for local playback to work.
- Android has three separate layers holding slot/transition state (Rust `playback/backend_shims/android.rs`, Kotlin `AndroidPlaybackPlugin.kt`, Kotlin `PlaybackService.kt`) — when touching Android playback, check all three rather than assuming one is authoritative (known rough edge, `adr/20` #6).
- `QueueSyncGateway` (`src-tauri/src/playback/queue_sync.rs`) is currently always `NoopQueueSyncGateway` in production — it's a seam for future Connect queue sync, not a real integration yet.

### Connect (multi-device / remote features)

`server/` (Go) is optional and separate from the Tauri app; it brokers WebSocket presence/shared-playback state (`server/internal/realtime/hub.go`) between clients already authenticated against their own OpenSubsonic server. Rust-side glue lives in `src-tauri/src/connect.rs` and `src-tauri/src/commands/connect.rs`; frontend glue in `src/features/connect/`. The Connect wire **types** (`ConnectPlaybackState`, `ConnectPlaybackCommand`) are generated from the Rust source of truth into `server/internal/realtime/connect_types_gen.go` (see the Type bridge section), so their shape cannot drift. The queue-mutation **reducers** are intentionally *not* unified: Rust (`controller.rs`) runs when Connect is off, Go (`hub.go`) runs when Connect is on, and the two never run concurrently. The single invariant both must preserve — what `playNextQueueLen` means (`region = [currentIndex+1, +len)`) — is documented in `docs/playback-queue-semantics.md`. The frontend's `isPlayNextQueueIndex` (`src/features/playback/usePlayback.ts`) is a read-only display helper, not a third reducer. (Was `adr/20` #8 / a Tier 1 debt; see `docs/known-issues.md` 解決済み for the rationale.)

### Settings

Settings have defaults/normalization/migration logic duplicated across `src-tauri/src/models/settings.rs`, `src-tauri/src/app_settings.rs`, `src-tauri/src/commands/settings.rs`, and `src/features/settings/service.ts`. Treat Rust as authoritative when defaults conflict (per `adr/20` #2); don't assume the TS-side default is correct without checking Rust.

### Android native code location

Android's Kotlin implementation lives under `src-tauri/gen/android/app/src/main/java/com/innsb/transonic/` (`MainActivity.kt`, `playback/AndroidPlaybackPlugin.kt`, `playback/PlaybackService.kt`, `playback/RustPlaybackBridge.kt`). Despite living in `gen/android` (a Tauri-generated project tree), these files are hand-authored and version-controlled — this is a known structural wart (`adr/20` #9), not accidental generated-file drift.

## ADRs (`adr/`)

Read `adr/README.md` before creating a new ADR. Key rules:
- ADRs record past decisions and reasoning, not future plans/TODOs — never write "what to do next" in an ADR, and never consult an ADR to find out what to do next.
- Create a new ADR file for new decisions; only edit an existing one if the user says "fix" (correction to a past entry uses strikethrough + a dated addendum, not deletion).
- Numbered sequentially (`N-slug.md`), with an author/date/version header — see existing files for the exact format.
- Not a place for hard architecture/system docs (those belong in `docs/`).

## Working conventions (from AGENTS.md)

- When asked to "research"/「調査」, "consider"/「検討」, or "investigate", make no code changes.
- Read current code rather than relying on TODOs or prior descriptions of intent.
- Don't run full Tauri builds speculatively; `tsc` + `cargo check` + tests cover most verification needs.
- Run tests when you've changed test files; no need to proactively report that you skipped running tests when there's a good reason.
- Don't worry about surfacing git status/diffs to the user mid-task unless directly relevant to the assignment.

### PowerShell-only constraints (this repo assumes PowerShell, not bash-isms)
- No Linux-style heredocs (`<<EOF`, `<< 'PY'`).
- No `sed`/`grep` in PowerShell — use `Select-String` etc. instead.
- Path/file operations should go through PowerShell.
- Encoding/line endings: Markdown/YAML/TOML/text → UTF-8 no BOM, LF. CSV → UTF-8 with BOM, CRLF. PowerShell 7.x scripts → UTF-8 no BOM, LF. PowerShell 5.x scripts → UTF-8 with BOM, LF.
